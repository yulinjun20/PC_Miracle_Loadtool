## 0. 一句话摘要

废除两套旧下载协议，凡是「往设备落一个文件」都走同一套：

```text
Start（类型 / 名字 / 大小 / 校验） → 分包 Data → End（整文件校验并落盘）
```

以后新增文件类型（如 SC App、WIFI、Logo 或更多），只加 `file_type` 编号和设备落盘规则，**不必再开新下载命令族**。

## 1. 背景与目标

### 1.1 现状问题（将被废除的部分）

当前 PC 工具存在**两套互不兼容的下载路径**：

| 路径 | 握手 | 帧校验 | 下载命令 | 典型用途 |
|------|------|--------|----------|----------|
| 旧 OS / Firmware | `'T'` → `'R'`/`'S'` | LRC 或 CRC32，**CMD 仅 1 字节** | `0xB0`/`0xB1`（VOS）；另有 Boot `0xC0`/`0xC1` | OS / Boot |
| 旧 App 文件 | `'L'` → `'A'` + DES 认证 | **CRC16-CCITT，CMD 2 字节** | `0xB200` / `0xB202` / `0xB204` | App / Font / Param / Data |

问题：

1. **扩展差**：新类型（SC App、WIFI、Logo…）只能继续堆分支或再开一套命令。  
2. **实现双份**：PC / 设备都要维护两套组包、分包、结束逻辑。  
3. **字段不统一**：旧 `0xB200` 用 24 位长度、固定 38 字节头；OS 路径又是另一套块格式。  
4. **整文件完整性弱**：旧路径缺少统一的「会话级整文件哈希/CRC」约定（依赖设备侧各自实现）。

### 1.2 本协议目标

1. **统一**：所有可下载文件走同一 Start / Data / End 会话。  
2. **可扩展**：`file_type` 表可往后加；未知类型设备应明确拒绝，PC 可跳过继续下一项。  
3. **可对齐**：字段、字节序、错误码写死，减少「靠猜 PC 行为」的对接成本。  
4. **工厂可扩展**：同一协议支撑一拖一与一拖多；多设备是 PC 编排，不改线命令。
5. **破坏性升级**：新旧下载命令**不混用**；配对升级 PC + 设备固件。

### 1.3 明确不改 / 明确废弃

| 能力 | 说明 |
|------|------|
| **Comm set** | 串口选择、波特率表、打开/关闭串口逻辑保持。开发者与工厂下载进行中均**锁定** Comm set（D32/D33）。工厂模式下**隐藏** Comm set 页（D38）；波特率仍在该页设置，工厂使用上次保存值（D39）。 |

| **DES 双次认证** | **永远关闭（D5）**：开发者与工厂**均不认证**；LoadTool **界面不放**「开启认证」开关；跳过 `0xB100..0xB103`，握手成功后直接进入下载会话（或 Sync time）。线协议可保留认证命令号供将来，但 **v1 永不启用**。 |

## 2. 设计原则

1. **一个文件 = 一个会话**。会话内不允许夹杂其他文件的 Data。  
2. **类型驱动落盘**。设备根据 `file_type`（及 App 时的 `slot_or_id`）决定写入分区/路径；`name` 不以类型定死固定名（见第 7 节）。  
3. **失败可继续**。多文件批量下载时，单项失败应返回明确错误码；PC 默认跳过该项继续下一项（与现 Download 页「失败跳过」一致）。  
4. **Start 协商分块上限**。设备在 Start 应答里返回 `chunk_accept`（可下调 PC 请求的 `chunk_max`）。更完整的能力位/能力查询留给 **v2**（见第 8 节一句说明）。  
5. **一拖多不改线协议**：多设备 = PC 多会话并行；禁止跨设备共享半开会话状态。  
6. **校验分层（两层各管一事）**：  
   - **帧层 CRC16**：覆盖整帧 `CMD+LEN+DATA`，防线路比特错、粘包切错。  
   - **会话层**：整文件 `file_hash` = **CRC32**（D1）；每块强制 **chunk_crc（CRC32）**（D4）。块 CRC 校验的是「本块文件净荷」本身，即使帧 CRC 通过，也能发现应用层组包/缓冲错误；整文件 CRC 在 End 再验一次防漏块/错序。  
7. **v1 写死的传输常量（不是可配开关）**：不压缩；每块必带 `chunk_crc`；不支持从中间偏移续传（见 6.1 / 6.2）。

## 3. 底层传输（复用现有 CRC16 帧）

**物理链路（已确认）**：与旧通讯下载相同，走 **USB VCP**（USB 虚拟串口）。PC 侧表现为 COM 口；工厂扫「全部 COM」即扫 USB VCP 枚举出的串口。本协议**不**另定 USB 自定义类或其它总线。

本协议**不重新发明串口帧**，复用现有应用管理 CRC16 帧（经 USB VCP 收发）：

### 3.1 帧格式

| 字段 | 长度 | 说明 |
|------|------|------|
| STX | 1 | 固定 `0x02` |
| CMD | 2 | 大端：`CMD/256`，`CMD%256` |
| LEN | 2 | 大端：DATA 字节数 |
| DATA | LEN | 本协议命令载荷 |
| CRC16 | 2 | CRC16-CCITT，覆盖 **CMD+LEN+DATA** |

- 总长 = `LEN + 7`。  
- 应答状态习惯：DATA[0] 为结果码（`0` = 成功），与现 CRC16 业务命令一致。  
- 建议单帧 DATA 上限与现实现对齐（PC 侧 historically 约 8900；业务分块见下文 `chunk`）。

### 3.2 会话前置流程（开发者 / 工厂同一套）

```text
打开 COM/USB-VCP 串口并确认成功（D64；失败则不得发握手）
  → 仅当打开成功后：握手 'L' / 'A'（开发者与工厂相同；工厂应答 DATA 可按 10.5 带可选 SN）
  →（可选）CMD_CHANGE_BAUD 0xB000/0xB001
  →（v1 永不启用，D5）跳过 DES 认证 0xB100..0xB103
  → 【一个或多个】文件下载：非 OS = 本协议会话；OS = 过渡期可走旧路径（D23）
  →（开发者可选）Sync time 0xB30A — 与下载互斥，D55：同任务不可与文件下载并存
  → CMD_FINISH_ALL 0xB400（拼写 Finish，见 D11）→ 关串口
```

> **OS 过渡例外（D23）**：在设备支持统一会话前，**仅下载 OS** 时仍可使用旧握手 `'T'`/`'R'`/`'S'` 及 LRC/CRC32 单字节 CMD 帧（`0xB0`/`0xB1`）。非 OS 文件下载**不得**走该旧路径。  
> 旧 Boot 下载路径**废弃**（D2）。  
> **不**为工厂另发明第二套握手命令；差异仅在应答 DATA 是否携带 SN（10.5）。

---


> **打开口先于握手（D64）**：LoadTool **必须先成功打开**目标 COM/USB-VCP 口，**之后才允许发送握手**（新协议 'L'/'A' 或过渡期旧 OS 'T'…）。打开失败（占用、权限、口不存在等）时：**不得发握手**；**开发者提示错误并停止**；**工厂静默跳过该口**、不占 12 路槽位，稍后重试打开。
>
> **开发者握手重试（D65）**：开发者模式下握手**沿用现有紧循环**——发出 `'L'`（或旧 OS `'T'`）后，每次读超时约 **20ms**，失败立即再发，最多约 **10000 次**；**不采用**「固定 3 次、间隔 2 秒」。点 Stop 可提前中止。（工厂空闲口仍按 D19 每 **2 秒**重试，与开发者紧循环不同。）
## 4. 命令号（已锁定，D8）

> **已定（D8）**：下载会话命令维持下表；与 Sync `0xB30A`、Finish `0xB400` 一并使用。避开现有 `0xB200`~`0xB205` 与 `0xB300` 段。

| Opcode | 方向 | 名称 | 作用 |
|--------|------|------|------|
| `0xB210` | PC → 设备 | `CMD_FILE_DL_START_REQ` | 开始下载会话 |
| `0xB211` | 设备 → PC | `CMD_FILE_DL_START_RSP` | Start 应答 |
| `0xB212` | PC → 设备 | `CMD_FILE_DL_DATA_REQ` | 发送一块数据 |
| `0xB213` | 设备 → PC | `CMD_FILE_DL_DATA_RSP` | Data 应答 |
| `0xB214` | PC → 设备 | `CMD_FILE_DL_END_REQ` | 结束会话并请求落盘校验 |
| `0xB215` | 设备 → PC | `CMD_FILE_DL_END_RSP` | End 应答 |
| `0xB216` | PC → 设备 | `CMD_FILE_DL_ABORT_REQ` | 中止当前会话（可选但强烈建议） |
| `0xB217` | 设备 → PC | `CMD_FILE_DL_ABORT_RSP` | Abort 应答 |

**相关控制命令（保留，非下载会话载荷）**：

| Opcode | 名称 | 说明 |
|--------|------|------|
| `0xB30A` | `CMD_SET_TIME` / Sync time | 校时；不属于 Start/Data/End |
| `0xB400` | `CMD_FINISH_ALL` | 任务结束；拼写为 **Finish**（D11：改正拼写，**不**再兼容错误 `FINSH`） |

**废除 / 过渡例外**：

| 旧命令 | 说明 |
|--------|------|
| `0xB200` / `0xB201` | 旧 Load File Start（**废除，D42/D43**：设备端从未对接，须新建 `0xB210+`；PC 非 OS 只走新会话） |
| `0xB202` / `0xB203` | 旧 Load File Data（**废除**） |
| `0xB204` / `0xB205` | 旧 Save File（**废除**） |
| `0xB0` / `0xB1` | 旧 VOS 数据/结束（1 字节 CMD 帧）。**过渡期仅 OS 可继续使用（D23）**；设备支持统一会话后废除 |
| `0xC0` / `0xC1` | 旧 Boot 数据/结束（**Boot 已废弃，D2**；不再维护旧 Boot 路径） |
| `'T'`/`'R'`/`'S'` 握手 | **过渡期仅服务于 OS 旧下载路径（D23）**；非 OS 下载使用 `'L'`/`'A'` |

控制类命令（改波特率、认证命令号、设备树、校时、`0xB400` 等）**不在废除之列**（**认证永远关、无 UI 开关**，见 D5）。

## 6. 公共字段与字节序

### 6.1 通用约定

| 约定 | 选择 |
|------|------|
| 整数字节序 | **大端（网络序）**，与现 CMD/LEN 及旧 24 位长度拼法一致风格 |
| 字符串 | UTF-8；字段为固定宽度时 **NUL 填充**，不含保证的结尾 NUL 时可按「有效长度 + 填充」解析 |
| `proto_ver` | 本文件为 **1** |
| 空会话 | 禁止：`size == 0` 时 Start 应被拒绝（除非某类型明确允许空文件；默认不允许） |
| 整文件哈希 | **CRC32**（4 字节，`file_hash`）（D1） |
| 默认 `chunk_max` | **4096**；设备可在 Start 应答中下调（第 12 节） |
| 压缩 | **v1 常量：不压缩**；载荷始终为原始文件字节（D6） |
| `chunk_crc` | **v1 常量：每块强制 4 字节 CRC32**（D4）；不是可关开关 |
| 续传 | **v1 不支持**；会话始终从偏移 0 开始传完整文件（D7） |

### 6.2 Start 请求载荷（`0xB210`）

定长头 + 变长名（双方按同一张表）：

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 1 | `proto_ver` | 协议版本，当前 `1` |
| 1 | 1 | `file_type` | 见第 5 节 |
| 2 | 1 | `slot_or_id` | **仅 App（type=2）填应用号**；其余类型恒 `0`（D4） |
| 3 | 1 | `name_len` | `name` 字节数，`0..32`（上限 32） |
| 4 | 4 | `size` | 整文件字节数，`uint32` |
| 8 | 4 | `file_hash` | 整文件 CRC32（D1） |
| 12 | 2 | `reserved` | **v1 填 0**（预留；不作可配 flags） |
| 14 | 2 | `chunk_max` | PC 希望使用的最大分块 DATA 净荷；默认请求 **4096**；设备可在应答中下调 |
| 16 | `name_len` | `name` | UTF-8 逻辑名（**不含路径**）；`name_len=0` 表示空名 |

> **v1 传输常量（写死，不是 Start 位标志）**：不压缩；每块 Data 必带 `chunk_crc`。  
> **是否重启**：只看 **End 应答的 `reboot` 字段**（6.7）；Start **不**再携带「下完重启」标志。

### 6.3 Start 应答载荷（`0xB211`）

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 1 | `status` | `0` 成功可传；非 0 见错误码 |
| 1 | 1 | `proto_ver_ack` | 设备支持的协议版本（可为协商后的版本） |
| 2 | 2 | `chunk_accept` | 设备接受的最大分块净荷（≤ 请求的 `chunk_max`；可下调） |
| 4 | 4 | `reserved` | **v1 填 0**（占位对齐；PC/设备均忽略语义） |
| 8 | 2 | `reserved2` | **v1 填 0** |

> v1 **不**描述、**不**实现从非零偏移续传。字段表保留 4+2 字节占位仅为布局稳定，语义留待 v2 再定义（若需要）。

### 6.4 Data 请求载荷（`0xB212`）

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 4 | `offset` | 本块在文件中的起始偏移（从 0 递增） |
| 4 | 2 | `data_len` | 本块 `data` 长度 |
| 6 | 4 | `chunk_crc` | **必有**：对本块 `data` 的 CRC32（D4） |
| 10 | `data_len` | `data` | 原始文件字节（v1 不压缩） |

### 6.5 Data 应答载荷（`0xB213`）

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 1 | `status` | `0` 成功 |
| 1 | 4 | `next_offset` | 设备期望的下一偏移（通常 = `offset + data_len`）；用于快速发现不同步 |

### 6.6 End 请求载荷（`0xB214`）

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 4 | `size` | 再次声明总长度（须与 Start 一致） |
| 4 | 4 | `file_hash` | 再次声明整文件 CRC32（须与 Start 一致） |

设备应：核对已收字节数 → 计算整文件 CRC32 → 与 `file_hash` 比较。

- **校验成功（接收阶段）**：将本文件保留为**临时/待安装对象**（尚未对运行区生效，见 D49）；应答 `status=0`。多文件场景下**不要**在此时最终提交/安装。  
- **校验失败或接收中途失败（D48）**：设备**立即删除当前临时下载文件**，返回错误并释放会话；**不**保留待下次。  
- **整次任务成功后（D48）**：安装阶段完成后，**删除**本任务相关临时下载文件（已锁定）。  
- **仅勾选单项且无「先收后装」拆分时**：仍可在 End 成功后直接进入该类型的安装/提交，成功后同样删除临时文件；失败则立即删除当前临时文件。

### 6.7 End 应答载荷（`0xB215`）——**重启信号唯一来源**

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 1 | `status` | `0` 本文件接收校验成功（多文件时多为已入临时区，见 D47/D48/D49） |
| 1 | 1 | `reboot` | `1` = 设备将重启或复位通信；PC 需等待后再继续；`0` = 本文件接收/落盘完成且**此刻不重启**（多文件场景常见，见 D47） |

> PC **只根据本字段**判断是否需要在下一项前做握手轮询等待；不要从 Start 或其它命令推断重启。  
> **多文件（D47）**：OS（及其它需安装的类型）在「仅收文件、尚未安装」阶段，End 应答应 **`reboot=0`**，以便 PC 继续传后续文件；全部收齐后再进入安装阶段，那时若需重启，再在对应安装完成的应答（或最后一次 End / Finish 约定）里置 `reboot=1`。

### 6.8 Abort（`0xB216` / `0xB217`）

请求可仅含 `status_reason`（1 字节）或空 DATA。设备丢弃未提交的临时对象并释放会话。

## 7. 命名与落盘规则（已锁定，D3）

**原则（D3）**：`name` **不以类型定死固定名**；设备落盘位置以 **`file_type` 为准**。除 Data 外，PC 可将 `name_len=0`（空名）。

| file_type | PC 填入的 `name` | 设备落盘语义 |
|-----------|------------------|--------------|
| OS (1) | **可空** | OS 分区/槽；**多文件任务中先只接收、不立即重启**（D47）；需重启时由 **End.`reboot`=1**（或安装阶段）告知 PC |
| App (2) | **可空**（也可带本机名，设备可忽略） | 应用槽；**`slot_or_id` = 应用号**（D4）；**整次任务结束后再生效/安装**（D49） |
| Param (3) | **可空** | 参数区 / Env；内容格式见 `EnvFormat.md`；**整次任务结束后再生效**（D49） |
| Data (4) | **应带本机文件名**（去掉路径与盘符，保留扩展名） | 按名存储；**同名覆盖**（仅**安装阶段**成功后生效，见 D10/D49） |
| Font (5) | **可空** | 字库区 |
| SC App (6) | **可空** | 安全芯片固件槽；**整次任务结束后再安装**（D49/D45） |
| WIFI (7) | **可空** | WIFI 固件槽；**整次任务结束后再安装**（D49/D45） |
| Logo (8) | **可空** | Logo 资源槽；**整次任务结束后再生效/安装**（D49） |

**`slot_or_id`（D4）**：仅 App 使用（应用号）；**其余类型恒为 0**。

- [ ] 临时文件：整次任务成功后删除；下载失败立即删除当前临时文件（D48，不保留待下次）；各类型整次任务结束后生效（D49）

**通用限制建议**：

- `name` 禁止包含 `\ / : * ? " < > |` 以及路径穿越 `..`。  
- Data 名长度建议 ≤ 32 字节（UTF-8）。  
- Param 文件大小建议上限 **128KB**（与现 ENV 一致）。  
- 其他类型上限由设备在 Start 应答中拒绝过大 `size`。

## 8. 完整性算法（已锁定，D1）

| 方案 | 用途 | v1 决议 |
|------|------|--------|
| **CRC32（4 字节）** | `file_hash`、`chunk_crc` | **采用** |

**v2 预留（一句）**：更强哈希（如 SHA-256）、设备能力位、能力查询等留待 v2 再定；v1 不实现、不占用可配开关。

**已定实现要点**：

- `file_hash`：**CRC32**，多项式与现有 `QuickCrc32`（或双方书面约定的同一实现）对齐；定稿实现时写明初值/异或值。  
- `chunk_crc`：同 CRC32；**每块强制 4 字节**（与帧 CRC16 分工见第 2 节原则 6）。

> 若产品后续有「防伪造固件」需求，应在安全启动/签名链上解决，而不是仅依赖下载会话哈希。

## 9. 消息时序

### 9.1 单文件成功路径

```text
PC                              设备
 | ---- FileDl Start (0xB210) ---> |
 | <--- Start RSP   (0xB211) ----- |
 | ---- FileDl Data (0xB212) ---> |   } 重复直到 offset+len == size
 | <--- Data RSP    (0xB213) ----- |   }
 | ---- FileDl End  (0xB214) ---> |
 | <--- End RSP     (0xB215) ----- |   （看 reboot；多文件收文件阶段应为 0，见 D47）
```

### 9.2 单文件失败 / 中止

- Start 被拒：不进入 Data；PC 记录错误，按策略跳过（计入该文件失败），**继续后续项**（D68）。  
- Data 失败：PC 可对**同一 offset** 重试（建议最多 3 次，与现网习惯接近）；仍失败则 Abort，结束本会话，**记录失败并继续下一项传输**（D68）。  
- 用户点 Stop：PC 发 Abort，结束本会话，不再开始后续项。  
- End 校验失败：设备不得提交落盘；PC 视为本文件失败，**继续下一项**（D68）。  
- **安装阶段**某一项失败：记录失败，**继续按 D53 安装下一项**（D69）；不因单项安装失败中止整台任务的其余安装。

### 9.2a Start 前 PC 本地校验（D66 / D67）

在真正打开口/握手/传文件之前，LoadTool 先做本地检查（开发者与工厂相同）：

- **Param（D66）**：若勾选 Param，但本机 Param/`.env` 文件 **JSON 校验失败** → **英文提示**，**不开始**本次任务（不握手、不传任何项）。  
- **OS（D67）**：若勾选 OS，但文件大小 **不在允许范围** → **英文提示**，**不开始**本次任务。  

（路径空 / 文件不存在仍按 D61；未勾选按 D60。）

### 9.3 多文件批量（Download 页）

建议顺序：

**安装顺序（D53，固定）**——全部接收完成进入安装阶段后，按此顺序逐个安装（只装本任务实际勾选/展开出的类型；缺项跳过）：

```text
OS → Font → Logo → Param → Data → SC App → WIFI → App
```

**传输编排**：PC 可按安装顺序传，也可先传完所有勾选项再统一安装；**安装阶段必须遵守 D53**。**Sync time 不与下载同任务**（D55）：开发者若勾 Sync time，则本次任务**只做校时**（`0xB30A`），不含任何文件下载；不进安装顺序。

**Bale（D54）**：**仅 PC 本地解包** → 把包内各项按对应 `file_type` 分别开会话下发。设备端**没有**、也**不得定义** `file_type=Bale`；设备**收不到、也不存**名为 Bale 的整包；安装顺序里**没有 Bale 这一步**（勾了 Bale = 解包后的子项按 D53 安装）。

规则：

1. 每一项（含 Bale 内每一子文件）= **独立会话**。非 OS：独立 Start/Data/End。**OS（过渡期，D23）**：走旧 `'T'`/`'R'`/`'S'` + `0xB0`/`0xB1`，不走 `0xB210+`；**开发者与工厂均如此**，且可与同任务内新协议文件混排；设备支持统一会话后，OS 也改为独立 Start/Data/End。  
2. **Continue-on-fail（D68 / D69）**：**传输阶段**某一项失败：记录该失败，**继续下一项传输**（D68）；**安装阶段**某一项失败：记录该失败，**继续下一项安装**（D69）；UI 汇总成功/失败。用户 Stop 仍立即中止后续项。  
3. **多文件：先收齐再安装 / 再重启（D47）**：勾选了多项时，**OS 传完后设备不得立即重启**；PC 继续按顺序把其余已勾选文件全部传完。全部接收（及校验）完成之后，设备再 **按 D53 顺序逐个安装**；需要重启时再重启（可安装一项重启一项，或按设备能力批量安装后重启——实现细节见设备实施说明）。**仅勾选 OS 一项**时（**开发者与工厂均如此，D47**）：该台/该口 **收完即安装并重启**，不必再等其它类型。物理链路为 **USB VCP**（与旧下载相同，已写入 D47）。  
3a. **生效时机（D49）**：**App / Font / Param / Data / SC App / WIFI / Logo** 均在**整次任务结束后**（全部目标文件接收完成之后）再进入安装/生效；接收阶段 End 成功**不等于**已对设备运行区生效。  
3b. **临时文件清理（D48）**：  
    - 整次任务**成功**（接收 + 安装完成）：**删除**本任务相关临时下载文件。  
    - 下载过程中**失败**（含 Abort、校验失败、写失败等）：设备**立即删除当前临时下载文件**；**不**保留待下次。  
3c. **工厂多台安装节奏（D50）**：一拖多时**每台自己收完就自己装**，**互不等待**其它台；一台进入安装不影响其它台继续接收。  
3d. **进度与文案（D51 / D52）**：  
    - **开发者**：进度条为**整次任务总进度**；状态栏同时显示**当前正在传的文件名**（如 `App 3/7`）。  
    - **工厂**：每一行进度为**该台**的整次任务总进度，并显示该台当前文件名。  
    - **UI 文案使用英文**（D52）。  
4. **安装后的等待（D9 / D58，配合 D47）**：只有设备通过 **End.`reboot`=1**（或安装阶段等价信号）明确要求重启时，PC 才做 **握手轮询 + 总超时**；若仍走旧 OS 路径且因「仅 OS」等原因会重启，沿用旧等待/重连逻辑。多文件收文件阶段 End 应为 `reboot=0`，PC **不要**在每次仅 OS 收完后进入长等待。**总超时固定 20 秒（D58）**；期间点 **Stop 立即停止等待并结束任务**。
5. **Bale（D54 / D56）**：**仅 PC 侧解包**，再对包内各项分别开会话；设备端**无 Bale 文件类型**，收不到/不存名为 Bale 的整包；安装顺序**无 Bale 步骤**（见 D53）。v1 **禁止**把整包当作单一 `file_type` 下发。解包后**缺某类子项则跳过**，**有的继续下载/安装**（D56），不因缺项整任务失败。
6. 与 Bale 勾选互斥的类型：App / Font / Param / Data / SC App / WIFI / Logo（产品层互斥；协议层无硬性禁止）。


**Start 前校验（D60 / D61）**：开发者与工厂点 Start 时——
- **未勾选任何下载项**：提示选择要下载的文件（英文 UI，例如 `Please select files to download.`），**不开始**。
- **已勾选但路径为空**：提示补全路径，**不开始**。
- **已勾选但文件不存在**：提示文件不存在，**不开始**。
### 9.4 Sync time（独立选项，与下载互斥）

校时仍走控制命令 `0xB30A`，**不属于** Start/Data/End。

**LoadTool UI（D34 + D55）**：

- **仅开发者模式**提供 Sync time 勾选；工厂模式不提供。
- Sync time 为**单独选项**，**不与下载项一起**勾选执行。
- 与任一文件下载勾选互斥：OS / App / SC App / WIFI / Font / Param / Data / Logo / Bale。
  - 勾选了**任一**下载项 → **禁止**勾选 Sync time；
  - 勾选了 Sync time → **禁止**勾选任一下载项。
- 因此一次 Start：**要么**只做文件下载（可多文件），**要么**只做 Sync time，二者不同时出现在同一任务中。

### 9.5 Finish（`0xB400`）

任务全部结束后发 `CMD_FINISH_ALL`（`0xB400`）。载荷/拼写以 **Finish** 为准（D11）；**不**再兼容历史错误拼写 `FINSH`。

- [ ] 临时文件：整次任务成功后删除；下载失败立即删除当前临时文件（D48，不保留待下次）；各类型整次任务结束后生效（D49）

## 10. 下载界面模式与工厂一拖多（Developer / Factory）

> **为什么写这一节**  
> 产品需要两套下载界面：**开发者模式（Developer）** 与 **工厂模式（Factory）**。  
> 线缆上的下载命令仍然是第 4～9 节那一套 Start / Data / End，不另开「总线广播命令族」。  
> 握手与开发者相同（`'L'`/`'A'`）；工厂仅在应答 DATA 中按 10.5 可选带回 SN。  
> 模式相关决议 **以第 14 节决策总表为准**；本节只写行为说明，避免与总表重复两份。

### 10.1 两套下载界面

| 模式 | 目标用户 | 同一时刻与设备关系 | 端口策略 |
|------|----------|--------------------|----------|
| **开发者模式（Developer）** | 研发 / 实验室 | **只与一台设备通讯** | 操作员在界面选定 **一个** COM；工具只使用该口 |
| **工厂模式（Factory）** | 产线灌装 | **最多同时 N=12 台** | 下载进行中仍 **持续扫描空闲串口**；发现空闲口则对其发 **同一套握手**，就绪后纳入下载队列 |

两种模式的文件勾选 / 路径配置相互独立（D15）；波特率均读 Comm set（D17）；工厂隐藏 Comm set 页时使用**上次保存的波特率**（D38/D39）；下载进行中两侧均**锁定 Comm set**（D32/D33）；两模式互斥运行（D22）。

**模式切换 UI（D16）：** 同一 **Download** 页**顶部**「开发者 / 工厂」切换（开关或分段按钮），**不**拆成两个主页签。下载进行中**禁止切换模式**，须先 Stop 再切（D41）。**两侧 Download 页均无设备树（D26）**：开发者侧 = Comm set 选定单口 + 本模式独立文件勾选/路径 + **独立 Sync time 选项（与下载勾选互斥，D34/D55）** + Start/Stop；工厂侧 = 最多 12 路状态列表（有 SN：**COM + SN + 进度 + 状态**；无 SN：**COM + 进度 + 状态**，D27/D28）+ 本模式独立文件勾选/路径（可勾 Bale，D35；**无** Sync time，D34）+ 下载（无树、无 Reflush/Del）。**工厂模式隐藏** Comm set 页与 Edit param 页（D38/D37）；**Task bale 页始终可用**（D36）。

### 10.2 开发者模式

1. 操作员在 **Comm set** 选定对应串口（COM）；Download **只使用该口**（核对确认）。  
2. 工具按选定串口与设备通讯；**同一时刻只和一台设备通讯**。  
3. 不需要后台扫其它空闲口；不启动多会话 fan-out。  
4. 握手 `'L'`/`'A'`；单文件成功路径、重试、Abort；多文件先收齐再安装（D47）；仅当 End.`reboot`=1 时握手轮询等待：复用第 9 节。  
5. **无设备树 UI**（D26）：不提供 Reflush / Del app / Del sub file；本模式只有文件勾选区 + Start/Stop。  
6. 文件勾选/路径与工厂模式**完全独立**（D15）。  
7. Start～Stop 间 **锁定 Comm set**（不可改串口/波特率）（D32）。  
8. **Stop**：**只停止当前口**会话（Abort 尽力而为）（D40）。  
9. 可勾选 **Sync time**（D34）；与任一下载勾选**互斥**（D55）——勾下载则不可勾 Sync time，勾 Sync time 则不可勾下载。  
10. 可进入 **Edit param**、**Task bale**、**Comm set** 页（下载未进行时；Task bale 始终可进，D36）。

### 10.3 工厂模式

```text
          ┌─────────────────────────────────────┐
          │  任务配置（勾选 OS/App/…、路径、顺序） │
          │  文件字节 + file_hash 只计算一次      │
          └──────────────┬──────────────────────┘
                         │  fan-out（最多 12 路）
     ┌───────────────────┼───────────────────┐
     ▼                   ▼                   ▼
 会话#1 / COMa      会话#2 / COMb      会话#k / COMx
 Start→Data→End     Start→Data→End     Start→Data→End
 设备 A              设备 B              设备 …
                         ▲
                         │
              后台持续扫描空闲 COM → 同一握手 L/A → 加入
```

要点（决议编号见第 14 节）：

1. **最大台数 12**（D12）。已满 12 路时新空闲口 **暂不握手**（D20），有槽位释放后再纳入。  
2. **扫描全部 COM**；已占用口不管（D13）。  
3. Start～Stop 间对空闲口 **每 2 秒**重试握手；一直无响应也不移出扫描（D19）。  
4. **谁握手成功谁开始下**（D14）；无齐套屏障。  
5. **会话相互独立**：每个 COM 一套握手 / Start→Data→End / Abort（**不认证**，D5）；一台失败不中断其它台。**每台自己收完就自己装，互不等待**（D50）。  
6. **文件内容共享（同批次）**：本模式勾选清单下的文件字节、`file_hash` / `chunk_crc`、Bale 解包结果全批次只算一次；串口句柄、会话 offset 不共享（无认证，D5）。  
7. Start～Stop 间 **锁定勾选/路径**（D21）。  
8. **总 Stop（D40）**：**停止全部口**并**停止扫描**；向进行中会话发 Abort（尽力而为）；已成功台不回滚。  
9. **不要求**真总线广播、设备间互听互等。  
10. **无设备树 UI**（D26）：只要状态列表 + 下载；不提供 Reflush / Del。  
11. 文件勾选/路径与开发者模式**完全独立**（D15）。  
12. **OS 过渡（D23）**：工厂任务中的 OS 也走旧协议；可与同任务内新协议文件混排（谁握成功谁按序下）。  
13. **整次任务成功后（D29）**：立刻释放该串口槽位，并继续扫描新空闲口纳入新人。  
14. **整次任务失败后（D30）**：释放该串口槽位，记录该台失败（界面统计即可，不写日志文件，D70），并继续扫描新人；不因一台失败停止全局扫描。  
15. Start～Stop 间 **锁定 Comm set**（D33）。  
16. **可勾选 Bale**（D35）；与开发者勾选配置相互独立。  
17. **不提供 Sync time 勾选**（D34）；互斥规则 D55 仅约束开发者 UI。  
18. **隐藏 Comm set 页与 Edit param 页**（D38/D37）；波特率使用 Comm set **上次保存值**（D39）。  
19. **Task bale 页仍可用**（与模式无关，D36）。

### 10.4 状态显示与 SN

| 情况 | UI 一行应显示（D27 / D28） |
|------|-----------|
| 设备 **已有 SN** | **COM + SN + 进度 + 状态**（进行中 / 成功 / 失败 / 已停止等；**进度 = 该台整次任务总进度**，另显示**当前文件名**，见 D50/D51） |
| 设备 **没有 SN** | **COM + 进度 + 状态**（不伪造 SN；**进度 = 该台整次任务总进度**，另显示**当前文件名**，见 D50/D51） |

SN 由握手应答带回（D18）；无 SN 时 `sn_len = 0`。线格式见 10.5。整次任务成功/失败后释放串口并继续扫描，见 D29 / D30。**进度 = 该台整次任务总进度**，并显示当前文件名（D51）。**UI 文案为英文**（D52）。


**槽位提示（D59）**：工厂下载进行中，状态区始终用英文显示当前活动路数（例如 `Active: 3/12`）；已满 12 路时额外提示 `Slots full`，并对新空闲口暂不握手（配合 D20）。

**握手失败（D63）**：工厂扫到某口握手失败（非本产品或拒绝）时，**忽略该口本轮**，**不占用 12 路槽位**；按 D19 间隔 **2 秒**后再试该口；**不移出**扫描列表。
（若连串口都打不开，按 D64 处理：**静默**跳过、不发握手、不占槽、稍后重试打开。）
### 10.5 握手应答中的可选 SN（统一握手，工厂常用）

开发者与工厂均使用 **`'L'` → `'A'`** 同一套握手。设备可在握手应答 DATA 中带回固定头 + 可选 SN（大端；外层仍为 CRC16 帧）：

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 1 | `hs_ver` | 握手载荷版本，当前 `1` |
| 1 | 1 | `hs_status` | `0` = 握手成功可纳入下载；非 0 = 拒绝/忙等 |
| 2 | 1 | `sn_len` | SN 字节数；**无 SN 时为 `0`** |
| 3 | `sn_len` | `sn` | UTF-8 或设备约定字节；**仅当 `sn_len > 0` 时存在** |

规则：

- **有 SN**：`sn_len = N`（**最长 32 字节，D57**；`1..32`），其后紧跟 `N` 字节 SN；工厂 UI 一行显示 **COM + SN + 进度 + 状态**（D27）；进度为该台总进度+当前文件名（D51）；文案英文（D52）。  
- **无 SN**：`sn_len = 0`，**不出现** SN 数据字节；工厂 UI 一行显示 **COM + 进度 + 状态**（D28）；进度为该台总进度+当前文件名（D51）；文案英文（D52）。  
- PC 解析时必须以 `sn_len` 为准，不得假定固定长度 SN 字段。  
- 开发者模式也可同样解析（有则显示，无则忽略）；开发者主路径仍是单口通讯。

### 10.6 协议层：必须「每设备独立会话」

- 对设备 *i*：同一握手 →（**不认证**，D5）→ **要么**按序各文件 Start / Data / End（可选 Finish），**要么**仅 Sync time `0xB30A`（**仅开发者**，且与下载互斥，D34/D55）→（可选 Finish）。同一任务不同时含文件下载与 Sync time。  
- 设备 *i* 与 *j* **不共享**「当前 offset / 半开 Start」状态。  
- **「一拖多」是 PC 编排问题，不是新的线命令。**

### 10.7 与单台流程的关系

```text
开发者模式：  1 选定 COM × 1 会话 × 多文件顺序
工厂模式：    ≤12 端口 × ≤12 会话 ×（每会话内仍是多文件顺序）+ 后台持续扫空闲口并握同一套手
```

**Task bale 页始终可用**（D36），与模式无关。**工厂模式下隐藏 Edit param 与 Comm set 页**（D37/D38）；开发者模式下二者可进。Edit param 若使用：**仍按单台操作**。Download 页（开发者/工厂）**不提供设备树**（D26）。

## 13. 迁移策略（破坏性变更）

### 13.1 OS 过渡例外（已定，D23）——**可以继续用旧 OS 协议**

**结论：可以。** 当前设备端 OS 下载协议与本文统一会话**不兼容**；若下载 OS 时强制改用新协议，可能导致 **OS 无法更新**。

因此迁移期约定：

1. **仅 OS** 下载可继续使用旧路径：`'T'`/`'R'`/`'S'` 握手 + `0xB0`/`0xB1`（1 字节 CMD + LRC/CRC32 帧）。
2. **其余文件类型**（App / Font / Param / Data / SC App / WIFI / Logo 等）一律使用本协议 Start/Data/End（`0xB210+`）；**废除**旧 `0xB200` 族（**D42/D43**：设备从未对接 `0xB200`，须按新协议新建；PC 非 OS 不再发 `0xB200`）。
3. 本例外为**过渡期**安排，**不是**长期双栈目标；设备端实现统一会话并验证 OS 更新可靠后，OS 也应切到 `0xB210+`，再删除旧 OS 路径。
4. 设备端现状参考路径（勿当作本仓库子目录）：`E:\MyProject\UN650\ML160T\UN650-ML160T_SDK\haoming\master\UN650-SDK_RTOS\UN650-ML160T-SDK_RTOS`。  
5. **开发者与工厂均适用**本例外；工厂一拖多任务中的 OS 同样走旧协议。
6. 同一任务内允许「旧协议 OS + 新协议其它文件」混排（按项切换路径，不在同一文件项内混用）。

### 13.2 其它类型与总体步骤

1. **配对发布（非 OS，D42/D43）**：新 PC 对非 OS **废除 `0xB200`**，只发 `0xB210+`；设备端 **从未实现 `0xB200`**，须 **新建** `0xB210+` 统一会话（非补齐旧协议）。旧 `0xC0` Boot 路径按 D2 废弃。
2. **OS 与非 OS 可阶段性并存**：同一 Download 任务中允许「OS=旧路径 + 后续项=统一会话」（开发者/工厂皆然）；**不要**在同一文件项内混用两套命令。
3. **不长期双栈**（推荐）：OS 迁入统一会话后，关闭旧 OS 路径，减少测试矩阵。
4. **文档与枚举同步**：`file_type`、命令号、CRC 初值写进本文件与设备头文件注释。
5. **回归清单**：OS（旧路径过渡）/ App / Font / Param / Data / SC App / WIFI / Logo / Bale 多文件 / 失败跳过 / Stop 中止 / **多文件 OS 传完不重启、收齐后再安装**（D47）/ 仅当 `reboot=1` 后等待 / 校时 / Finish；OS 切统一会话后再回归 End.`reboot` 路径。
6. **旧文档**：`LoadTools_通讯协议说明.md` 中下载相关章节标记为 **Deprecated**（OS 章节注明「过渡期仍有效，见 D23」），并链接本文。
7. **Boot**：旧 Boot 下载路径标记废弃，不再实现新路径（D2）。
8. **Finish**：`0xB400` 使用正确拼写 Finish；移除对 `FINSH` 的兼容（D11）。
